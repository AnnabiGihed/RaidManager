# ADR-0028: Keep the test environment's secrets in a GitHub environment

- Status: Proposed
- Date: 2026-10-03
- Deciders: Gihed Annabi

## Context

Locally, every secret lives in the Aspire AppHost's user secrets (README, "Sign in with Discord locally"). Release
v0.3 deploys RaidManager to a test environment on one OVH VPS-1, run with Docker Compose files that `aspire publish`
generates from the AppHost, and deployed by a GitHub Actions workflow that copies images over SSH
([ADR-0027](0027-run-the-test-environment-on-one-ovh-vps.md)). Spike #103 asks where the deployed secrets are kept,
how they reach the containers, how the deploy workflow signs in to the server, and how each secret is rotated.

ADR-0027 already answers the hosting question: one VPS, with no cloud identity service in front of it. The secrets in
scope:

| Secret | Used by | Source today |
| --- | --- | --- |
| Discord OAuth client secret (and the client id, sensitive but not secret) | Website | AppHost parameters `discord-client-secret`, `discord-client-id` |
| Discord bot token | API ([ADR-0022](0022-check-discord-roles-at-action-time.md)), later the bot | AppHost parameter `discord-bot-token` |
| Website key ([ADR-0011](0011-website-session-and-api-trust.md)) | Website and API | AppHost parameter `website-service-key`, generated |
| SQL Server password | SQL Server, API | AppHost parameter `sql-password`, generated by Aspire |
| Pivot.Framework feed token | Image builds | Repository secret `PIVOT_PACKAGES_TOKEN` |
| Deploy credential for the server | Deploy workflow | None yet |

## Decision

### The store: a GitHub environment named `test`

- **The secrets of the test environment are environment secrets of a GitHub environment named `test`**, whose
  deployment branch rule admits `main` only (owner decision on #103). GitHub encrypts them, nobody can read them back,
  and only a workflow job that targets `test` from `main` receives them. Values that aren't secret are environment
  variables of `test`, so they stay readable.
- **The owner enters every value**, on their own machine, with `gh secret set <name> --env test`, which reads the value
  from the prompt and not from the command line. The website key and the SQL password are random values the owner
  generates there, for example with `openssl rand -base64 48`. No value passes through the repository, an issue or
  chat, and the agent never handles one.
- **Names:** the secrets are named after the keys that `aspire publish` writes into the `.env` template for the AppHost
  parameters, so the workflow maps them one to one:

  | AppHost parameter | In `test` | Kind |
  | --- | --- | --- |
  | `discord-client-id` | `DISCORD_CLIENT_ID` | variable |
  | `discord-client-secret` | `DISCORD_CLIENT_SECRET` | secret |
  | `discord-bot-token` | `DISCORD_BOT_TOKEN` | secret |
  | `website-service-key` | `WEBSITE_SERVICE_KEY` | secret |
  | `sql-password` | `SQL_PASSWORD` | secret |
  | none (deploy workflow) | `DEPLOY_SSH_KEY` | secret |
  | none (deploy workflow) | `DEPLOY_HOST`, `DEPLOY_SSH_KNOWN_HOSTS` | variables |

  If the generated template names a key differently, #389 follows the template and corrects this table.

### Delivery: the deploy workflow writes the server's `.env` file

- At each deployment, the workflow (#389) writes `/opt/apps/raidmanager/.env` on the server from the `test` secrets and
  variables, then runs `docker compose up -d`, which passes the values to the containers as environment variables.
- The values travel only through the SSH connection's input: the job puts them in `env:` and pipes them to
  `umask 077; cat > .env.new; mv .env.new .env` on the server. They never appear in a command line, a `${{ }}`
  expression inside `run:`, the runner's disk or the job's log, where GitHub also masks them.
- The file is owned by `deploy` and readable by `deploy` only (mode 600). Members of the `docker` group can see a
  container's environment with `docker inspect`, but that group is root-equivalent on the server anyway, and only
  `deploy` belongs to it.
- Because the workflow rewrites the file at every deployment, a rebuilt server gets its secrets back from the next
  deployment, and the server's backup isn't the only copy.

### Deploy authentication: a dedicated SSH key

A VPS has no cloud identity service, so the OpenID Connect federation the spike asked about has nothing to trust it.
The workflow signs in with its own key instead:

- The owner generates an Ed25519 key pair used only by the workflow. The private key is the `DEPLOY_SSH_KEY` secret;
  the public key goes into `deploy`'s `authorized_keys` with the `restrict` option, which turns off forwarding,
  terminals and agent use. The owner's personal key stays separate, and the dashboard tunnel of ADR-0027 uses it.
- The workflow checks the server's identity against `DEPLOY_SSH_KNOWN_HOSTS` with `StrictHostKeyChecking=yes`. The
  owner records it after comparing the host key's fingerprint with the one shown at the server's first sign-in.
- The key gives as much power as the `docker` group, which is root on the server. That's why the `test` environment
  admits `main` only, and why a pull request's workflow never receives it.

### The feed token stays on the runner

`PIVOT_PACKAGES_TOKEN` stays a repository secret. The workflow restores packages on the runner before the images are
built, so the token never enters an image layer, the Compose file or the server.

### Rotation

| Secret | Who rotates it | When | How |
| --- | --- | --- | --- |
| Discord client secret | Owner | Yearly, and on any suspicion | Reset it in the Discord developer portal, update the secret, deploy. |
| Discord bot token | Owner | Yearly, and on any suspicion | Reset it in the portal, update the secret, deploy. |
| Website key | Owner | Yearly, and on any suspicion | Generate a new value, update the secret, deploy. |
| SQL password | Owner | Yearly, and on any suspicion | See below. |
| Deploy SSH key | Owner | Yearly, and on any suspicion | Add the new public key, update `DEPLOY_SSH_KEY`, deploy, then remove the old public key. |
| Feed token | Owner | Before it expires | As the README describes for the repository secret. |

- **Website key:** one deployment restarts the website and the API together. Until both run with the new key, a
  website request can get a 401 for a few seconds; the test environment accepts that. Rotating without that gap needs
  the API to accept the previous key as well during a short overlap, which is left to the production decision.
- **SQL password:** SQL Server applies `MSSQL_SA_PASSWORD` only when it creates its data volume, so changing the secret
  alone breaks the API's connection. The owner first changes the password inside SQL Server
  (`ALTER LOGIN sa WITH PASSWORD = ...`, run with `sqlcmd` in the container, typed at the prompt), then updates the
  secret and deploys.
- **After any leak**, rotate the secret at once and deploy; test data can be discarded if the database was reached.

### Environments

- **The test environment has its own Discord application**, "RaidManager Test", with its own client secret and bot
  token (owner decision on #103). Rotating a test secret never breaks the local run, and once the bot connects to
  Discord's gateway, a local bot and a test bot never answer the same events. Its redirect is
  `https://raidmanager-test.pivotsoftwares.com/signin-discord`.
- **No value is shared between environments.** Production, when a later release decides it, gets its own GitHub
  environment, Discord application and values, and can add required reviewers to its environment.

### Local development

Local development stays on the AppHost's user secrets and the local Discord application. It reads no remote store, so
a run on a laptop needs no network credential and can't reach a deployed secret.

## Follow-up work

- **#386 (under #153):** the owner creates the `test` environment with its `main` rule, the "RaidManager Test" Discord
  application and bot, and the deploy key pair; enters the values above; and installs the public key on the server.
  The agent writes the steps and checks the result without seeing any value.
- **#388 (under #375):** the test settings and the Discord redirect for the test application.
- **#389 (under #376):** the workflow job that targets `test`, pins the host key and writes `.env` as described.

## Consequences

**Positive**

- No new service or account: the store is the GitHub plan the repository already uses, and the `github-pages`
  environment shows that its plan supports environments.
- One place to change a secret, and one deployment to apply it; a rebuilt server needs no manual secret setup.
- Only workflow runs from `main` can read the secrets, and nobody can read them back from GitHub.

**Negative**

- The secrets sit in two places: GitHub, and the `.env` file on the server, readable by root and `deploy`.
- Whoever controls `main` or the workflow files controls the secrets, so the branch protection and review gates of
  ADR-0004 to ADR-0009 protect them too.
- The website key rotation causes a short burst of 401s, and the SQL password needs a manual step.

**Residual risk**

- A stolen deploy key gives root on the test server, and with it every test secret. Rotating all of them after such an
  event is the remedy; the server holds no production data.
- The website's Data Protection keys (ADR-0027) aren't encrypted at rest on the volume. That is accepted for test
  and is for the production decision to revisit.

## Alternatives considered

- **An `.env` file kept by hand on the server:** fewer GitHub secrets, but the server and its backup hold the only
  copies, and every rotation needs an SSH session.
- **An external vault** (Infisical, Bitwarden Secrets Manager, HashiCorp Vault): better audit and rotation tools, but a
  further service and a further credential to protect, which one test server doesn't justify.
- **Compose secrets mounted as files** instead of environment variables: they keep values out of `docker inspect`,
  but the Compose file `aspire publish` generates uses environment variables, and on this server the people who can
  run `docker inspect` can read the files too.
- **A mesh VPN or short-lived SSH certificates for the deploy:** narrower deploy credentials, but more moving parts
  than a dedicated, restricted key on a test server.
