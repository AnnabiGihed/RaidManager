# C# XML documentation (Pivot.Framework style)

Documentation is part of the code. Code without the required XML documentation is incomplete and is not proposed,
committed or approved. This skill merges the former `csharp-xml-documentation` and `csharp-documentation-summaries`
rules and aligns them with how Pivot.Framework is documented (≈97 % of its source files use the header below).

## 1. Type header — Author / Date / Purpose inside `<summary>`

Every type declaration (class, record, struct, interface, enum, delegate — including nested, `partial`, and test types) carries:

```csharp
/// <summary>
/// Author      : Gihed Annabi
/// Date        : 09-2026
/// Purpose     : Non-generic inbox service that wraps a context-specific <see cref="IInboxRepository{TContext}"/>
///              and exposes <see cref="SaveChangesAsync"/> for persisting inbox records.
///
///              Injected into non-generic consumers (e.g. <c>RabbitMQReceiver</c>) that must check and record
///              message consumption without being generic over <typeparamref name="TContext"/>.
/// </summary>
/// <typeparam name="TContext">The EF Core DbContext that contains the inbox table.</typeparam>
public sealed class InboxService<TContext> : IInboxService
```

- Exact labels and alignment: `Author      :`, `Date        :`, `Purpose     :` (padded to the same column); continuation lines of Purpose are indented to align under the text (`///              `). Blank `///` lines separate paragraphs.
- **Author** — full name of the developer who created the type: take it from `git config user.name`. Never "Claude", "Copilot", "AI", "Unknown" or an invented name; if git has no name and the user hasn't given one, ask.
- **Date** — creation month as **`MM-yyyy`** (`09-2026`).
- **Purpose** — what the type is responsible for **and why it exists**; it replaces a separate one-line summary, so the first sentence must state what the type is. Mention non-obvious design constraints (thread-safety, lifetime, which package registers it).
- Existing type **without** a header: author/date from the commit that created the file: `git log --diff-filter=A --follow --format="%an|%ad" --date=format:%m-%Y -- <path> | tail -1`. Existing header: never change Author/Date; update Purpose only if the responsibility changed.
- Partial types: full header on the primary declaration (file named after the type / `.razor.cs`); other parts get a normal `<summary>` saying what the part contains.
- `<typeparam>` for every generic parameter of the type, after the summary.

## 2. Members — what must be documented

| Member | Required |
|---|---|
| public / protected / internal properties, indexers, events, constants, enum members | `<summary>` (+ `<value>` when the meaning isn't obvious) |
| public / protected / internal methods, local functions at member level | `<summary>`, `<param>` per parameter, `<typeparam>`, `<returns>` for non-void (on `Task<T>` describe `T`), `<exception>` for every exception thrown directly (incl. guard clauses) |
| constructors (incl. the private/protected EF Core ctor) | `<summary>`, `<param>`, `<exception>` for guards |
| operators / conversions | `<summary>`, `<param>`, `<returns>` |
| overrides and interface implementations | `/// <inheritdoc />` (write a custom summary only when behaviour differs from the contract, and say how) |
| private methods | `<summary>` when the intent isn't obvious from the name (Pivot documents most private helpers) |
| private fields | `<summary>` for constants and non-obvious state (e.g. `Separator`, caches); injected dependency fields (`_logger`, `_dbContext`, `_repository`) may stay undocumented — their constructor `<param>` documents them |
| test methods | `<summary>` stating the behaviour verified ("Verifies that a successful publish marks the message as processed.") |

Generated code (`*.g.cs`, `*.Designer.cs`, `*.feature.cs`, `<auto-generated>`, EF migrations) is never edited or documented.

## 3. Wording (Pivot conventions)

- Complete sentences, capitalised, ending with a period. British spelling is used throughout Pivot (`Initialises`, `serialisation`, `behaviour`) — keep it consistent within the repo.
- Constructors: `Initialises a new <see cref="TypeName"/>.` (+ extra behaviour, e.g. "Validates that the identifier is not empty.").
  EF-only ctor: `Parameterless constructor reserved for EF Core materialisation.`
- Properties: `Gets …` / `Gets or sets …`; booleans `Gets a value indicating whether …`.
- Methods: third-person verb (`Creates`, `Maps`, `Persists`), never "This method …".
- `CancellationToken`: "A token to cancel the operation." (or "Cancellation token." consistently within a file).
- `Result`-returning members: document what success carries and which `Error` codes / `ResultExceptionType` failures are returned — callers can't infer it from the signature.
- Use `<see cref="…"/>`, `<paramref name="…"/>`, `<typeparamref name="…"/>`, `<see langword="null"/>`, `<c>code</c>`; renames then break the build instead of rotting the text.
- **Add information the signature doesn't carry** — purpose, side effects, units, ranges, nullability, thread-safety, thrown exceptions. `Gets the name.` on `Name` is not acceptable unless nothing more can be said; never *omit* a required summary to avoid an echo — improve it instead.
- Comments explain *why*, not *what*; restating code is deleted, not reworded (see `clean-code-comments`).

## 4. Documentation pass workflow (review or improvement)

A documentation pass never changes behaviour, signatures or logic — suggest refactors separately.
1. Scope: role of the code (library surface vs internal) and whether it's docs, readability or both.
2. Names first: a better name often beats a better summary; flag vague names.
3. Type headers: present, correct format, real author, `MM-yyyy`.
4. Non-private surface: summary + param/returns/exception/typeparam; `<inheritdoc />` on overrides/implementations.
5. Private code: intent comments where needed; remove narrating comments.
6. Report as **before → after** pairs:
   - `Member` — `File.cs:line` · *Before:* … · *After:* … · *Why:* (only if not self-evident)
   - then **Removals** (noise), **Readability suggestions** (renames/splits, recommendations only), **Next steps**.

Example:
> `ProcessOutboxMessagesAsync` — `OutboxProcessor.cs:40`
> *Before:* `/// <summary>Processes outbox messages.</summary>`
> *After:* `/// <summary>Publishes all unprocessed outbox messages in creation order, stopping at the first publish failure. Increments <c>RetryCount</c> and dead-letters the message once <see cref="OutboxRetryOptions.MaxRetryCount"/> is reached.</summary>`

## 5. Enforcement

`Directory.Build.props` (or per project): `<GenerateDocumentationFile>true</GenerateDocumentationFile>`. Pivot.Framework's
props don't set it yet — add it when you touch build configuration (see `clean-code-static-analysis`).

`.editorconfig`:
```ini
[*.cs]
dotnet_diagnostic.CS1591.severity = error   # missing XML comment on visible member
dotnet_diagnostic.SA1600.severity = error   # elements must be documented (StyleCop)
dotnet_diagnostic.SA1611.severity = error   # parameters documented
dotnet_diagnostic.SA1615.severity = error   # return value documented
dotnet_diagnostic.SA1618.severity = error   # type parameters documented
dotnet_diagnostic.SA1623.severity = none    # Pivot uses 'Gets …' but not always SA1623's exact form
dotnet_diagnostic.SA1633.severity = none    # no file-header banners; the type header replaces them

[*.{g.cs,Designer.cs,feature.cs}]
generated_code = true
```
`stylecop.json` — document exposed + internal elements, not private fields (matching §2):
```json
{ "settings": { "documentationRules": {
  "documentExposedElements": true, "documentInternalElements": true,
  "documentPrivateElements": false, "documentPrivateFields": false, "documentInterfaces": true } } }
```
Analyzers don't check Author/Date/Purpose — verify by hand.

## Review checklist
- [ ] Every type has the `Author / Date (MM-yyyy) / Purpose` header inside `<summary>`, real author from git, unchanged on edits.
- [ ] Every non-private member has a summary (or `<inheritdoc />`), with params, type params, returns and directly thrown exceptions.
- [ ] `Result`-returning members describe their failure codes/types.
- [ ] Summaries add information beyond the name; no narrating comments; no behaviour changed in a docs pass.
